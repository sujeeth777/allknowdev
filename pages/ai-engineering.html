STAGE 01 · PROGRAMMING & DATA

Python and practical math

Learn Python, notebooks, files, functions and core data handling. Build comfort with vectors, probability and graphs as they become useful.

  • Load, inspect and clean a small dataset.
  • Plot data and describe what you see.
  • Use Git and a virtual environment to keep work reproducible.
Try: a small data report with a written explanation of its limits.
STAGE 02 · MACHINE LEARNING

Train a simple baseline

Understand features, labels, train/test splits, overfitting and metrics before comparing sophisticated models.

  • Choose a public, well-documented dataset.
  • Compare a simple baseline to one improved model.
  • Check for leakage, class imbalance and misleading metrics.
Try: predict one outcome and explain errors, not just accuracy.
STAGE 03 · MODELS & APPLICATIONS

Build a model-powered feature

Explore a framework or model API only when it serves your task. Learn prompts or inference, structured outputs, latency and usage limits.

  • Create a small test set of realistic examples.
  • Handle missing, unexpected and low-confidence outputs.
  • Protect private data and keep keys out of client code.
Try: a cited document helper with a visible “check the source” path.
STAGE 04 · EVALUATE & OPERATE

Make quality measurable

Test real behaviour, monitor failures and document intended use. A model demo is not automatically a safe or reliable product.

  • Define success and failure cases before changing the system.
  • Review bias, privacy, security and misuse risks.
  • Record model, data and evaluation changes.
Try: publish an evaluation card with methods, results and known limitations.

PROJECT CHALLENGE

Build a question-answering study helper

Use a small set of public documents and make it easy to check whether an answer is grounded in the source.

  • Start with a fixed set of questions and expected sources.
  • Show references beside generated answers.
  • Test unsupported questions and conflicting information.
  • Document privacy, cost assumptions and known failure modes.
BEFORE YOU PICK A MODEL

Write down the job first

Some problems need search, rules, a database or a clear UI—not a model.

  • What does a useful result look like?
  • Can a smaller or simpler method meet the need?
  • How will you check correctness and harmful edge cases?
  • What data leaves your device, and what can that cost?
