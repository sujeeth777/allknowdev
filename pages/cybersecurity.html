PATH / 04 · DEFEND

Think like a defender.
Practise with permission.

Security work is grounded in systems knowledge, careful testing and responsible communication. Learn in local or explicitly authorised labs—never probe real systems without permission.

STAGE 01 · SYSTEMS FOUNDATIONS

Networking, Linux & web basics

Understand hosts, ports, DNS, HTTP, operating systems, permissions and how applications move data.

  • Inspect your own machine's processes and network settings.
  • Explain the lifecycle of a browser request.
  • Learn command-line and log-reading fundamentals.
Try: draw the request flow for a tiny app you run locally.
STAGE 02 · BUILD SECURELY

Identity, data & secure coding

Learn authentication, authorisation, input handling, dependency hygiene, secret management and safe defaults.

  • Use a threat-model checklist for a toy application.
  • Keep secrets and personal data out of source control.
  • Update dependencies and understand security advisories.
Try: review your own sample app against a secure-development checklist.
STAGE 03 · PRACTISE SAFELY

Labs & defensive investigation

Use a local lab or platform that explicitly permits practice. Learn to observe, reproduce and explain a finding without causing harm.

  • Read scope and rules before starting a lab.
  • Keep testing inside the provided environment.
  • Focus on evidence, impact and a safe remediation.
Try: complete a beginner web-security lab and write a remediation note.
STAGE 04 · COMMUNICATE & IMPROVE

Detection, response & reporting

Security improves when teams can understand what happened, what matters and how to reduce future risk.

  • Read logs and distinguish evidence from assumptions.
  • Prioritise fixes by impact and likelihood.
  • Write a clear, respectful report with reproduction boundaries.
Try: produce a short incident timeline from a provided training dataset.

PROJECT CHALLENGE

Harden a tiny demo app

Create or use an intentionally simple local application, then improve its defensive defaults.

  • Map the data and trust boundaries.
  • Review authentication, input validation and error handling.
  • Check dependencies and remove test secrets.
  • Write a concise list of changes and remaining risks.
SAFETY BOUNDARY

Permission comes first

Learning is not a reason to test systems outside a scope you are explicitly authorised to assess.

  • Use local labs, CTF challenges or written scopes.
  • Do not scan, access or disrupt third-party systems.
  • Stop when you reach the boundary of permission.
  • Follow responsible disclosure policies when applicable.
